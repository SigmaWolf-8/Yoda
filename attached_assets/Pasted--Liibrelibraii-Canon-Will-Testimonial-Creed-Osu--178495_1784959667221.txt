UNIFORM RESOURCE LOCATOR (URL) AN EDIFIED TREATISE

PROLOGVS

The identification of a resource within any information space is an accounting identity. In the double‑entry ledger of the Web every resource is an Asset, its Uniform Resource Locator the permanent account number. The URL is a structured character string governed by RFC 3986 (IETF, 2005), whose morphology maps directly onto the financial messaging framework of ISO 20022, the institution‑identifying BIC of ISO 9362, and the currency codes of ISO 4217. In the GAAP representation the total identification capacity of a URL is the sum of its debited locational liabilities and its credited nominal equities. The statement of identity is a symmetrical balanced equation:

\[
URL \equiv Scheme : Authority / Path ? Query \# Fragment
\]

Each component carries a unit of measurement: the dimensionless unit “character” as defined in ISO/IEC 80000‑13. The URL is therefore a financial instrument of information exchange, a SEPA‑compliant mandate that orders the retrieval or naming of a resource across the single euro payments area of data.

CAPVT I. QUID SIT URL

A Uniform Resource Locator is a compact string that uniquely nominates a resource and specifies its access mechanism. Double‑entry decomposition reveals two mutually exclusive asset classes: the locational liability (where the resource resides) and the name‑based equity (what the resource is, independent of location). Every URL is a URI; the converse is not necessarily true. In GAAP terms:

\[
Asset_{Resource} = Liability_{Location} + Equity_{Name}
\]

The resource asset is always perfectly balanced by the sum of its location obligation and its permanent nominal equity. This equation is the fundamental identity of web resource accounting and conforms to the double‑entry principle of Regulation (EU) No 260/2012 (SEPA) that mandates unambiguous end‑to‑end identification.

CAPVT II. SYNTAXIS VNIVERSALIS

The grand syntax is a five‑field message that follows the ISO 20022 “Party Identification” structure. Let the scheme be a Business Service code, the authority a BIC (ISO 9362), the path a structured remittance line, the query conditional parameters, and the fragment a proprietary end‑to‑end identifier. The algebraic form:

\[
URL = S \;:\; A \;\/\; P \;?\; Q \;\#\; F
\]

where:
\[
S \in \{ https, mailto, ftp, urn, \dots \} \quad \text{(ISO 20022 ExternalCodeSet)}
\]
\[
A = [userinfo@]host[:port] \quad \text{(host validated as BIC11 per ISO 9362)}
\]
\[
P = /seg_1/seg_2/\dots/seg_n \quad \text{(structured remittance information, pain.001)}
\]
\[
Q = key_1=val_1\&key_2=val_2 \quad \text{(payment conditions)}
\]
\[
F = anchor \quad \text{(end‑to‑end ID per SEPA rulebook AT‑41)}
\]

The grammar is a context‑free production that yields a deterministic finite automaton. The double‑entry constraint is that every opening delimiter ( //, ?, #) must be balanced by a closing contextual scope. The URL string length is an asset measured in octets, the unit of account being the ISO/IEC 8859‑1 code point, convertible to ISO 10646 with a fixed exchange rate (percent‑encoding). This isomorphism guarantees that any valid URL can be parsed by a generic algorithm, irrespective of the scheme, just as any SEPA credit transfer can be processed by any compliant payment service provider.

CAPVT III. URL: LOCATOR LIABILITY

A URL is a URI that bears a network location. It is a promise to deliver a representation: a debit of the resource from a specific host to the requesting agent. The prototypical URL:

\[
URL = https://www.example.com/path?search=uri\#section2
\]

is booked as:

\[
Dr.\; Resource\; Request\; (Client) \quad = \quad Cr.\; Representation\; Delivery\; (Server)
\]

The scheme https is the transport‑layer security service (ISO 20022 Business Service “HTTPS”), the authority is the BIC EXAMPLLXXX (fictitious, conforming to ISO 9362), the path is a structured remittance information line, the query string carries additional settlement conditions, and the fragment indicates the precise sub‑resource. The whole string is a SEPA‑compliant payment instruction: the client debits its attention account, the server credits the content account. The units of information transferred are bits (ISO/IEC 80000‑13), and the value is measured in utility, subjectively quantified by the user.

CAPVT IV. URN: NAME EQUITY

A URN is a URI that carries no locational liability; it is pure equity, a permanent name that persists through changes of custody. The pattern:

\[
URN = urn : NID : NSS
\]

where NID is a registered namespace identifier (e.g., “isbn”, “uuid”, “ietf”) and NSS is the namespace‑specific string. This maps to the GAAP equity account:

\[
Equity_{Name} = URN, \quad Liability_{Location} = 0
\]

Examples:
\[
urn:isbn:0-486-27557-4 \quad \text{(ISO 2108, a book’s permanent identity)}
\]
\[
urn:uuid:6e8bc430-9c3a-11d9-9669-0800200c9a66 \quad \text{(ISO/IEC 9834-8, a universally unique asset tag)}
\]
\[
urn:ietf:rfc:3986 \quad \text{(the standard itself as eternal equity)}
\]

Resolution of a URN into locations requires a separate resolution service (e.g., DDDS), analogous to a securities depository that maps ISIN (ISO 6166) to a custody location. The URN itself remains an invariant, a financial anchor that preserves the resource’s identity across all corporate actions.

CAPVT V. SALTUS PHILOSOPHICVS

The early web conflated “opening a document” with its address. Modern architecture distinguishes identity from action as rigorously as double‑entry bookkeeping distinguishes an account from a transaction. The URL is a nominal account; the HTTP method (GET, POST, PUT, DELETE) is the transaction type. The two are orthogonal:

\[
Action \perp URL
\]

The double‑entry for a retrieval:
\[
Dr.\; URL\; Identification \quad (Client\; requests\; identity)
\]
\[
Cr.\; Representation \quad (Server\; delivers\; state)
\]

And for a state‑changing operation:
\[
Dr.\; Resource\; State \quad (Client\; sends\; new\; state)
\]
\[
Cr.\; URL\; Identification \quad (URL\; remains\; unchanged)
\]

This separation, formalized in the REST architectural style, echoes the EU’s Regulatory Technical Standards on strong customer authentication (SCA): identity (the URL) is proven once, actions are authorised individually. The equation of state remains balanced.

CAPVT VI. URL, IRI ET MVNDVS VLTRA ASCII

The original URL specification was limited to a subset of ASCII. The Internationalized Resource Identifier (IRI), defined in RFC 3987, extends the set to the full Universal Character Set (ISO/IEC 10646). An IRI such as:

\[
IRI = https://例え.テスト/パス
\]

is equivalent, through a deterministic percent‑encoding algorithm, to a pure ASCII URL:

\[
URL = https://%E4%BE%8B%E3%81%88.%E3%83%86%E3%82%B9%E3%83%88/%E3%83%91%E3%82%B9
\]

The transformation is a unitary quantum gate:
\[
|URL\rangle = U_{pct} |IRI\rangle, \quad U_{pct}^\dagger U_{pct} = I
\]

No information is lost; the equity of the name is preserved. Modern browsers (user‑agent payment service providers) apply this gate transparently, ensuring that the SEPA‑wide reach of the URL is extended to all scripts without altering the underlying GAAP identity. Every character outside the ASCII range is accounted for as a series of octet‑denominated percent‑encoded entries, maintaining the integrity of the global information ledger.

CAPVT VII. PRINCIPIA AEDIFICANDI

A well‑designed URL obeys three permanent accounting principles, derived from the EU’s digital single‑market acquis:
1. Stability – It shall outlive changes of technology. A stable URL is an asset that never suffers impairment.
\[
\Delta URL_{t \to t+\Delta t} = 0
\]
2. Hackability – The hierarchical path must allow the user to ascend by truncating segments, just as a general ledger allows drilling down from control account to sub‑ledger.
\[
URL /seg_1/seg_2 \xrightarrow{truncate} URL /seg_1
\]
3. Semantic transparency – It shall reflect the resource’s nature, not the implementation detail.
\[
URL \propto Resource \; Content, \quad URL \perp Implementation
\]

These principles align with the “faithful representation” qualitative characteristic of IFRS and with the SEPA rulebook’s requirement that end‑to‑end identifiers be meaningful and persistent. The quality of a URL is a linear function:
\[
Q_{URL} = \alpha \cdot Stability + \beta \cdot Hackability + \gamma \cdot Semantic, \quad \alpha,\beta,\gamma > 0
\]

A URL that satisfies all three is a first‑class financial asset on the information balance sheet.

CAPVT IX. DE INTEGRITATE ARITHMETICA ET SECVRITATE

Integer overflow represents a structural vulnerability in financial computation. A fixed‑size integer container can wrap, falsifying the debit‑credit equality. To properly clean this risk, three principles are applied. First, monetary amounts are stored as rational pairs (numerator, denominator) or arbitrary‑precision integers, eliminating bounded overflow. Second, every transaction is subjected to an exact double‑entry check: the automaton transition function δ(state, entry) computes R_i − S_i exactly, using integer arithmetic per ISO/IEC 10967, and halts with rejection unless the difference is zero. Third, any operation that would overflow must raise a notification and abort, as mandated by ISO 10967‑1.

The automaton model is expressed as:
\[
\delta(\text{state}, \text{entry}) : \text{compute } \Delta = \sum_{i} R_i - \sum_{i} S_i, \quad \text{accept if } \Delta = \Theta_{\text{GPV}}, \text{ else reject}
\]
Because the integers are unbounded (type I with no maxint), overflow cannot occur. The verification is perfect; a non‑zero difference reveals a cooked book. Thus the double‑entry identity A = L + E is preserved against any overflow‑based fraud, and the URL, as an accounting identity, remains incorruptible.
